    條目¶

    W05-001　把按鈕文字抽成 START／STOP／RESTART 常數再分流¶

    • 關鍵字：START STOP RESTART setText getText equals 常數化
    • 來源：第七課 08:00–12:00｜L07_第七课_教學筆記.md；第八課 11:00–13:00｜L08_第八课_教學筆記.md
    • 要點：服務起停的三顆按鈕是靠「按鈕文字」決定行為的，所以文字必須先抽成類別常數， 再以 equals 比對分流。常數非 null 時放左邊，即使右邊是 null 也只會回 false； 反過來左邊是 null 就會拋空指針。
    • 程式碼：
    private final String START = "启动";
private final String STOP = "停止";
private final String RESTART = "重启";

    // 一律把「不會為 null 的常數」放在 equals 的左邊
if (START.equals(button.getText())) {
    // ...
} else if (STOP.equals(button.getText())) {
    // ...
}
    • 坑：畫面理解層曾把按鈕文字讀成 运行，與同一段出現的 START = "启动" 並存。 按鈕文字與常數必須逐字一致，因為 equals 比的就是字串；差一個字等於該按鈕完全沒有分支。 另：第七課講者口述一度把重啟常數唸成「exit」，最終命名為 RESTART。

    W05-002　用 operate(HBox top, Button... buttons) 可變參數一次綁定三顆按鈕¶

    • 關鍵字：operate Button... buttons setOnAction Lambda HBox top
    • 來源：第七課 08:00–12:00、16:00–20:00｜L07_第七课_教學筆記.md
    • 要點：三顆按鈕的事件處理不各寫一份，而是抽成一個接受「父容器＋可變參數按鈕」的方法， 以迴圈替每顆按鈕掛 setOnAction。把父容器一起傳進來，是為了讓事件處理內部 能遍歷同一個容器去做防呆置灰與事後的狀態刷新。
    • 程式碼：
    private void operate(HBox top, Button... buttons) {
    for (Button button : buttons) {
        button.setOnAction(event -> {
            if (START.equals(button.getText())) {
                // 尚未實作啟動邏輯
            } else if (STOP.equals(button.getText())) {
                Server.getInstance().shutdownInternal(false);
            } else if (RESTART.equals(button.getText())) {
                Server.getInstance().shutdownInternal(true);
            }
        });
    }
}

    呼叫端（必須在按鈕加入 root 之前呼叫）：

    operate(top, startButton, stopButton, restartButton); // 新增這行呼叫
    • 坑：事件綁定 API 在畫面層不一致——多數片段為 setOnAction（與口述一致）， 但第七課 12:00–16:00 與 44:00–48:00 兩段被記為 setOnMouseClicked。 兩者並存，筆記未判定，實作以口述的 setOnAction 為準。 另：第八課 07:00–09:00 另有一版用 setOnAction(event -> ...) 綁刷新按鈕， 屬同課的 ActionEvent 寫法（見 W05-015）。

    W05-003　點擊當下先把容器內所有按鈕 setDisable(true) 防重複點擊¶

    • 關鍵字：setDisable setDisable(true) forEach getChildren 防呆
    • 來源：第七課 16:00–20:00、24:00–28:00｜L07_第七课_教學筆記.md
    • 要點：JavaFX 的 Button 在處理耗時操作期間不會自己鎖住。點擊任一按鈕的第一個動作 必須是「把容器內所有子元件一起 setDisable(true)」，否則使用者可以在啟動跑到一半時 再點停止、再點重啟，把服務狀態弄亂。
    • 程式碼：
    // 點擊當下三顆按鈕全部鎖死，防止重複點擊
top.getChildren().forEach(child -> child.setDisable(true));
    • 坑：① top.getChildren().forEach 不能假設裡面全是 Button。 只要 HBox 裡放了 Spacer 或其他 Region，(Button) child 就會拋：
    Exception in thread "JavaFX Application Thread" java.lang.ClassCastException: class javafx.scene.layout.Region cannot be cast to class javafx.scene.control.Button
    at client.views.home.ServerHomeView.lambda$operate$2(ServerHomeView.java:55)
    at java.base/java.util.Iterable.forEach(Iterable.java:75)

    ② 置灰後一定要有辦法回來。 講者原話：「因為它拋了一個異常。拋了一個異常之後， 那麼後面的整個就全部完了、全部 GG 了。」所以 catch 必須包住整個業務流程， 且流程結束後要主動重設狀態（見 W05-004）。 ③ 實測後果：資料庫沒開時三顆按鈕全灰且不恢復，因為「點了啟動就一定成功」的預設是錯的。

    W05-004　changeButtonStatus 依服務實際狀態逐項重設按鈕可點擊性¶

    • 關鍵字：changeButtonStatus isOnline isActive setDisable Platform.runLater setText
    • 來源：第七課 28:00–32:00、44:00–48:00、48:00–49:00｜L07_第七课_教學筆記.md
    • 要點：按鈕的可用狀態必須「由後端實際狀態反推」，而不是由「我剛剛點了什麼」推論。 操作結束（成功或失敗）後重新讀一次狀態，再逐顆決定 disable。 講者最終定義的規則：服務未啟動 → 啟動鈕可點、停止鈕不可點、重啟鈕一直可點； 服務已啟動 → 啟動鈕不可點、停止鈕與重啟鈕可點；操作進行中 → 三顆全部不可點。
    • 程式碼：
    private void changeButtonStatus(HBox top) {
    boolean active = Server.getInstance().isActive();
    Platform.runLater(() -> top.getChildren().forEach(child -> {
        Button btn = (Button) child;
        if (active) {
            if (START.equals(btn.getText())) {
                btn.setDisable(true); // 伺服器運行中，禁用"啟動"
            } else {
                btn.setDisable(false); // 啟用"關閉"、"重啟"
            }
        } else {
            if (START.equals(btn.getText())) {
                btn.setDisable(false); // 伺服器關閉中，啟用"啟動"
            } else {
                btn.setDisable(true); // 禁用"關閉"、"重啟"
            }
        }
    }));
}

    背景執行緒每秒輪詢的另一版：

    private void changeButtonStatus(HBox top) {
    new Thread(() -> {
        while (true) {
            try {
                boolean online = Server.getInstance().isOnline();
                Platform.runLater(() -> {
                    top.getChildren().forEach(child -> {
                        Button btn = (Button) child;
                        if (START.equals(btn.getText())) {
                            btn.setDisable(online);   // 服務已啟動 → 啟動鈕不可點
                        } else if (STOP.equals(btn.getText())) {
                            btn.setDisable(!online);  // 服務未啟動 → 停止鈕不可點
                        } else {
                            btn.setDisable(false);    // 重啟鈕永遠可點
                        }
                    });
                });
                Thread.sleep(1000);
            } catch (Exception e) {
                // 例外處理（畫面中未見具體列印日誌，僅捕捉）
            }
        }
    }).start();
}

    單顆按鈕改文字的另一版：

    private void changeButtonStatus(VBox top) {
    Platform.runLater(() -> {
        Button btn = (Button) top.getChildren().get(0);
        if (Server.getInstance().isOnline()) {
            btn.setText("关闭服务端");
        } else {
            btn.setText("开启服务端");
        }
    });
}
    • 坑：① isOnline() 與 isActive() 並存，多數片段用 isOnline()，44:00–48:00 段用 isActive()；是否為同一方法、兩者用途是否不同，筆記未確認。 ② 本頁三個版本並存（三顆切 disable／背景輪詢／單顆改文字），推測是教學過程中的迭代版本， 未收斂成單一寫法；實作前要先選定一種策略再改文案，否則兩套規則會打架。 ③ 畫面理解層曾產出連續兩個條件完全相同的 else if (title.equals(btn.getText()))， 不可能通過編譯，屬重寫失真；實際應為 else if (STOP.equals(...)) 這類條件。 ④ 若沿用單顆改文字版，千萬不要把刷新按鈕放進同一個容器（見 W05-018）。

    W05-005　必須先 addAll 再 changeButtonStatus¶

    • 關鍵字：getChildren().addAll changeButtonStatus(top) show() 呼叫次序
    • 來源：第七課 28:00–32:00、40:00–44:00、48:00–49:00｜L07_第七课_教學筆記.md
    • 要點：狀態連動是靠遍歷 top.getChildren() 實作的，所以在按鈕還沒被加進容器之前呼叫 等於對空集合做迴圈，狀態設定全部落空。show() 內的呼叫次序是固定的。
    • 程式碼：
    top.getChildren().addAll(startButton, stopButton, restartButton);  // 必須先 addAll
operate(top, startButton, stopButton, restartButton);
changeButtonStatus(top);    // 否則 top.getChildren() 可能是空的
readServerConsole(center);  // 把日誌 TextArea 綁進定時讀取

    講者原話：「當然一定是它在 getChildren().addAll() 以後，然後再去改變它的狀態啊。 否則的話，這個 top 在這裡去 getChildren 的時候，就有可能是一個空啊。」

    • 坑：本片實際發生的 bug 就是「灰掉之後回不來、切走再切回來才恢復」。 另一個順序陷阱：operate(top, ...) 是在把 UI 加進 root 之前呼叫的， 寫反了同樣拿不到正確的節點樹。切到別的菜單再切回來狀態會正常， 是因為「永遠會調用我們的 show 方法嘛，調用我們的 show 方法就會刷新」。

    W05-006　起停操作丟進 new Thread，UI 更新一律用 Platform.runLater¶

    • 關鍵字：new Thread Platform.runLater Not on FX application thread 單執行緒 isActive
    • 來源：第七課 24:00–28:00、48:00–49:00｜L07_第七课_教學筆記.md；第八課 05:00–07:00｜L08_第八课_教學筆記.md

    W05-007　啟動走 Server.getInstance().init()，結束後必須重查狀態¶

    • 關鍵字：Server.getInstance() init() shutdownInternal(boolean restart) finally 異常處理
    • 來源：第七課 08:00–12:00、20:00–24:00、44:00–48:00｜L07_第七课_教學筆記.md
    • 要點：按鈕事件的業務邏輯只有兩條路：啟動走 init()，其餘走 shutdownInternal(restart)（false = 停止、true = 重啟）。 整段必須包在 try 裡，且狀態更新要放在 finally，否則啟動失敗時按鈕會永久卡在灰色。
    • 程式碼：
    private void operate(HBox top, Button... buttons) {
    for (Button button : buttons) {
        button.setOnAction(event -> {
            // ① 點擊當下三顆按鈕全部鎖死，防止重複點擊
            top.getChildren().forEach(child -> child.setDisable(true));

            // ② 耗時操作丟到子執行緒，避免 JavaFX UI 執行緒被卡死
            new Thread(() -> {
                try {
                    if (START.equals(button.getText())) {
                        Server.getInstance().init();                        // 啟動
                    } else {
                        // shutdownInternal(restart)：false = 停止，true = 重啟
                        Server.getInstance().shutdownInternal(RESTART.equals(button.getText()));
                    }
                } catch (Exception e) {
                    Log.error("服務起停，發生異常", e);     // 必須用自己的 Log 工具類，不要用 LogFactory
                } finally {
                    // ③ 切回 JavaFX 執行緒更新 UI（子執行緒直接改 UI 是不合法的）
                    changeButtonStatus(top);
                }
            }).start();
        });
    }
}
    • 坑：① 方法名不一致：口述明確為 Server.getInstance().init()； 第七課 20:00–24:00 段的畫面理解層讀成 Server.getInstance().run()。以 init() 為準。 ② shutdownInternal 的參數被誤用：44:00–48:00 段的畫面記為 Server.getInstance().shutdownInternal(START.equals(button.getText()))， 傳的是 START 而非 RESTART，點重啟鈕時會得到 false（等同關閉），語意錯誤。 ③ Log.error 訊息字串三版並存：口述為「服務起停，發生異常」， 畫面另記為 Log.error("操作-服务器管理出现异常。", e) 與 log.error("操作{}时发生异常", button.getText(), ex)。以口述為準。 ④ 上一課若把整個 ui 套件刪掉，服務啟動時會找不到 ConfigServer／ConfigServerResolver／ GmCommand 等實體類而報錯：

    • 來源：第七課 32:00–36:00、36:00–40:00、40:00–44:00｜L07_第七课_教學筆記.md；第八課 21:00–24:00｜L08_第八课_教學筆記.md

    private void readServerConsole(TextArea textArea) {
    Timer timer = new Timer();
    timer.schedule(new TimerTask() {
        @Override
        public void run() {
            File logFile = new File(ServerConstants.DIR_LOG + "logs/out.log");
            // 明確指定 GBK，避免中文亂碼
            StringBuilder lineBuilder = new StringBuilder();
            try (InputStreamReader isr = new InputStreamReader(new FileInputStream(logFile), "GBK");
                 BufferedReader reader = new BufferedReader(isr)) {
                String line;
                while ((line = reader.readLine()) != null) {
                    lineBuilder.append(line).append("\n");
                }
            } catch (Exception e) {
                // 忽略：檔案可能尚未產生

            final String text = lineBuilder.toString();

                textArea.setText(text);
                textArea.setCaretPosition(textArea.getDocument().getLength());  // 永遠捲到最後一行
            });
        }
    }, 0, 1000);   // 口述：每 1 秒
}

    W05-014　Timer 必須提升為類別欄位並在 destroy() 裡 cancel()¶

    • 關鍵字：java.util.Timer TimerTask destroy() super.destroy() timer.cancel() 記憶體洩漏 MenuBaseStruct
    • 來源：第八課 02:30–05:00、09:00–11:00、21:00–24:00｜L08_第八课_教學筆記.md
    • 要點：把 Timer 寫成 show() 內的區域變數是定時任務洩漏的通用模式—— 每次切走再切回菜單就再 new 一個，而舊的那個從來沒被停掉。 解法兩步：把 timer 提升為類別欄位，並覆寫父類的 destroy()， 在其中 timer.cancel() 後設為 null。
    • 程式碼：
    // 類別最上方
private Timer timer;

    @Override
public void destroy() {
    super.destroy();
    if (timer != null) {
        timer.cancel();
        timer = null;
    }
}

    恢復刷新時重新啟動定時任務：

    // 在 refresh 類方法中，new Timer 之後記得賦值給類別欄位
timer = new Timer();
timer.schedule(new TimerTask() { ... }, 0, 1000);   // 週期 1 秒
    • 坑：① 宣告了 Timer 卻沒賦值，destroy() 就是空的。 本課親自示範了這個 bug： 畫面上 timer 一直是 null，取消邏輯完全沒作用。要點是 timer = new Timer(); 必須取代原本的區域變數宣告 Timer timer = new Timer();。 講者原話：「我們只定義了一個 timer，並並沒有把它實際上的用起來。」 ② cancel() 之後務必設 null。 只 cancel() 不設 null，下次進入選單時 if (timer == null) 的判斷不成立，恢復刷新的分支會被跳過。第八課 04:00 附近的 中間版本只有 timer.cancel();，是修正過程中尚未補齊的一版。 ③ super.destroy() 一定要在最前面。 父類的 destroy() 負責把 root 從父容器移除 並設為 null；順序顛倒會碰到已失效的節點樹。 ④ 講者講清楚兩層職責分工：父類 destroy() 做「所有選單都要做的操作」， 子類 destroy() 做「本類別專屬的清理」。 ⑤ Timer 讀取 logs/out.log 的寫法也出現在 ConsoleView 頁簽的 destroy() 中，形狀相同。 ⑥ 跨頁參照：資源釋放只靠設 null 交給 GC，但「服務啟停」永不釋放，見 W14-015。

    W05-015　加「暫停刷新／繼續刷新」Toggle，解決每秒 positionCaret 搶走選取焦點¶

    • 關鍵字：REFRESH_STOP REFRESH_START positionCaret getText() 當狀態旗標 ActionEvent
    • 來源：第八課 05:00–07:00、09:00–11:00、11:00–13:00、21:00–24:00｜L08_第八课_教學筆記.md
    • 要點：定時任務每秒把 caret 拉到最後一行，會把使用者剛選好的文字焦點搶走， 導致「想把報錯日誌複製到群裡問問題」這件事做不到。因此在右側加一組 Toggle 按鈕： 點下去先改文字，再 timer.cancel()；再點一次改回文字並重新啟動定時任務。
    • 程式碼：
    private final String REFRESH_STOP  = "停止刷新";
private final String REFRESH_START = "自动刷新";

    Button refreshButton = new Button(REFRESH_STOP);
refreshButton.setOnAction(event -> {
    if (REFRESH_STOP.equals(refreshButton.getText())) {
        if (timer != null) {
            timer.cancel();
            timer = null;
        }
        refreshButton.setText(REFRESH_START);
    } else {
        refreshButton.setText(REFRESH_STOP);
        // 後續在此處補上了 regThreadTask(textArea); 以重新啟動任務
    }
});

    「异常日志」頁的另一組文案：

    if (refreshButton.getText().equals("自动刷新")) {
    refreshButton.setText("停止自动刷新");
    if (timer == null) {
        // 初始化並啟動 timer 的邏輯
    }
} else {
    refreshButton.setText("自动刷新");
    if (timer != null) {
        timer.cancel();
        timer = null;
    }
}

    2023-11-26 17:16:13:955 [INFO] >>> 开始自动刷新异常日志文件...
2023-11-26 17:16:16:952 [INFO] >>> 停止自动刷新异常日志文件...
    • 坑：① 用按鈕的 getText() 當狀態旗標很脆弱。 本課自己就踩到了： REFRESH_STOP 的值先寫成 "停止"，後來又改成 "停止刷新"。 若改文字當下已有實例存在，REFRESH_STOP.equals(getText()) 會失效、Toggle 會整個反轉。 更穩的做法是用一個 boolean refreshing 欄位判斷狀態，文字只負責顯示。 ② 語意方向容易寫反：按鈕一開始建立在「刷新開啟中」的狀態，所以初始文字是 REFRESH_STOP（暫停刷新），而點下去的第一個動作是「改文字」。 ③ 同一語意四種措辭並存：暂停刷新 / 停止刷新 / 自动刷新 / 停止自动刷新； 照抄字串比對邏輯很容易在改文案時壞掉。 ④ 顏色語意被講者自己推翻：暫停刷新並非危險操作、繼續刷新也非安全操作， 最後決定維持黑色——但這也意味著按鈕外觀無法一眼區分當前狀態， 使用者仍必須靠文字判斷。

    W05-016　日誌寫入 UI 從整段 setText 改成 appendText ＋ positionCaret¶

    • 關鍵字：appendText setText positionCaret getLength setScrollTop SwingUtilities.invokeLater
    • 來源：第八課 05:00–07:00｜L08_第八课_教學筆記.md；第七課 36:00–40:00｜L07_第七课_教學筆記.md
    • 要點：每 tick 都整段 setText 替換會造成 UI 刷新／捲動條卡頓。 第八課改成 appendText 附加，並用 positionCaret 自動捲到最下方。 注意 appendText 解決的是效能，解決不了焦點被搶——兩者是不同問題，需分開處理。
    • 程式碼：
    Platform.runLater(() -> {
    textArea.appendText(sb.toString());
    // 自动滚到最下方
    textArea.positionCaret(textArea.getLength());
    // textArea.setScrollTop(Double.MAX_VALUE); // Double.MAX_VALUE : scrollToEnd();
});

    Swing 版的對應寫法（第七課 36:00–40:00 段，與 JavaFX 版並存）：

    SwingUtilities.invokeLater(() -> {
    textLogs.setText(lineBuilder.toString());
    textLogs.setCaretPosition(textLogs.getDocument().getLength());
    // 移除了原本可能逐行 append 的做法，改為整體 setText
});
    • 坑：① 兩種自動捲動 API 不同且不等價：JavaFX 的 textArea.setCaretPosition(textArea.getDocument().getLength()) 與 textArea.positionCaret(textArea.getLength()) 並存，前者是第七課寫法、後者是第八課寫法。 ② UI 框架在整組筆記中混用：第七課 36:00–40:00 段用的是 Swing 的 JTextArea textLogs 與 SwingUtilities.invokeLater，與其餘片段的 JavaFX 不同， 推測是講者參考舊的 Swing 版控制台程式碼所致，或辨識失真。

    W05-018　非啟停用的按鈕要放右側 VBox，不能塞進 top¶

    • 關鍵字：BorderPane setRight VBox right setSpacing setPadding changeButtonStatus(HBox top)
    • 來源：第八課 07:00–09:00、11:00–13:00、15:30–18:00｜L08_第八课_教學筆記.md
    • 要點：狀態連動是對 top 的 getChildren() 做 forEach，會統一改掉 top 底下所有按鈕。 所以任何不屬於服務起停的按鈕（例如刷新 Toggle）都不能放進 top，否則服務起停時它會被一起改掉。 講者的決策理由：要嘛在 forEach 裡額外排除它（「太麻煩了」），要嘛放別的容器—— 因為 root 是 BorderPane，右邊本來就該放一個 VBox，後續還能繼續擴充。
    • 程式碼：
    // BorderPane root 的右側容器
VBox right = new VBox();
right.setSpacing(10);

Button refreshButton = new Button(REFRESH_STOP);          // 預設是「開啟刷新」，故顯示暫停
refreshButton.setStyle("-fx-background-color: black; -fx-text-fill: white");
refreshButton.setPadding(new Insets(0, 0, 0, 10));       // 與左側拉開距離
// ... 中間包含按鈕點擊事件 setOnAction 與 Timer 邏輯 ...

right.getChildren().add(refreshButton);
root.setRight(right);

    呼叫端重構（把 new Button() ＋ setStyle() 換成靜態工廠）：

    Button stopButton    = ButtonUtil.createRedButton(STOP);
Button restartButton = ButtonUtil.createBlackButton(RESTART);
Button refreshButton = ButtonUtil.createBlackButton(REFRESH_STOP);
    • 坑：① 口述的內間距 5 與畫面讀出的 10 不一致（right.setSpacing(10)），兩者都記錄，衝突未解決。 ② root.setRight(...) 只認 BorderPane；若根節點換成別的佈局容器，右側 VBox 這套要重做。 ③ 按鈕文字 REFRESH_STEP 疑為誤讀，應為 REFRESH_STOP（逐字稿說的是傳入 refresh_top， 而 v002 的常數定義是 REFRESH_STOP = "停止刷新"）。 ④ ButtonUtil 的套件名兩種讀法：package m.util;（有明確右鍵 New → Java Class 動作， 以此為準）與 package ms.util;。講者口述只說「在 utils 這裡」， 且自嘲命名「我也不知道怎麼取名」——口頭是 buttonUtils，實際落地為 ButtonUtil（單數）。 ⑤ ButtonUtil 硬編 CSS 字串而非用 StyleClass，無法用偽狀態（:hover）與外部樣式表覆寫。
