    W16　協作流程與改版實作¶

    本頁為主題式重組，內容全部來自原始的 42 份逐片教學筆記，未引入外部資訊。 每條可獨立引用；條目 ID 穩定，請勿隨意改號。

    本頁來源 S4 是全批素材中畫面層與口述層最一致的一支片，但仍有 15 處細節互相矛盾 （Clone 網址帳號、Git 安裝路徑、安裝檔名、SDK 版本、開啟視窗選擇、Commit 訊息等）。 依本 wiki 規則，矛盾處一律並列不擇一，詳見各條「坑」與頁末總表。

    條目¶

    W16-001　硬性門檻：先成功提交一次 PR 才會被邀請為開發者¶

    • 關鍵字：PR Fork 開發者 倉庫成員 前置條件
    • 來源：S4 00:00–02:00、24:00–26:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：講者明講前置條件——必須先成功提交一次 PR，之後才會被邀請成為主倉庫的開發者。 收到邀請後點訊息按 确认加入 即完成（websocket 已推送，不需刷新）。 為什麼設這個門檻，三個理由逐字保留：(1)「怕有人搗亂」，怕直接給開發者權限後把 bug 傳上主倉庫； (2)「我想看一下你們到底有沒有這個能力」；(3) 希望對方自己漢化／貢獻的東西 留在自己的提交記錄與貢獻者名單裡，而不是發給講者代為提交。
    • 坑：這是硬性前置條件，不是建議。想跳過 fork 直推主倉庫會被拒。
    • 相關：見 W01-007（2.x-course 分支的由來）

    W16-002　完整參與流程共 16 個步驟¶

    • 關鍵字：Gitee Clone JDK 1.8 GBK checkout 2.x Pull Request 合併 remote
    • 來源：S4 全片｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：講者給的完整流程，逐字順序為： Gitee 開帳號 → 進入主倉庫點 Fork → 複製自己 fork 倉庫的 HTTPS 網址 → 裝 Git → 設 user.name / user.email → Clone 到本地 → IDEA 指定 JDK 1.8 與依賴 → 設編碼 GBK → 指定 Git 路徑 → checkout 2.x 分支 → 改碼 → Commit → 提交並推送 → 在 Gitee 新建 Pull Request → 主倉庫端審查與合併 → 被邀請為開發者並確認加入 → 改指 remote 為主倉庫 → 直接在主倉庫分支繼續提交。
    • 坑：這一支片完全沒有使用終端機版的 branch／add／commit／push 指令—— 分支切換、Commit、Push、Fetch 全部走 IntelliJ IDEA 的 Git GUI，PR 與合併全部在 Gitee 網頁。 照著這支片學會操作後，若換到純指令環境仍不會 git checkout -b／git add／git commit -m／git push。

    W16-003　Fork 之後要複製的是「自己倉庫」的網址¶

    • 關鍵字：Fork 克隆/下载 https://gitee.com/ zx993817
    • 來源：S4 00:00–04:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：Fork 之後會有一個「以自己名字開頭的 fork 倉庫」屬於自己，可以自己改、自己打包。 口述特別強調：「fork 完這個倉庫以後，然後我們複製一下自己倉庫，注意啊，是自己倉庫的地址。」 操作：在主倉庫頁面點 「Fork」 → 彈窗 「Fork 仓库」 → 目標選 zx993817 (个人) → 完成後上方提示 「当前分支落后 master 提交了 15 次提交...」 並出現 「创建 Pull Request」 按鈕 → 點 「克隆/下载」 複製 HTTPS 網址 https://gitee.com/zx993817/HeavenMS-Nap.git。
    • 坑：⚠️ Clone 網址帳號不一致——v000／v002 記錄為 zx993817/HeavenMS-Nap.git， 但 v001 同一個 Clone 視窗卻是 https://gitee.com/zjs091817/heaven-ms-nap.git（帳號與大小寫皆不同）。 兩者皆照登，未擇一。實作時以自己帳號下、剛 fork 出來的那個為準。
    • 相關：見 W16-010

    W16-004　裝完 Git 要重啟 IDEA，還要手動指定 Path to Git executable¶

    • 關鍵字：git-scm.com Git-2.41.0 <DRIVE>\Program Files\Git Path to Git executable 无法运行 Git
    • 來源：S4 04:00–08:00、18:00–20:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：到 git-scm.com 下載 64-bit Git for Windows Setup。本片手動把安裝路徑改為 <DRIVE>\Program Files\Git，其餘一路 Next 到 Finish，結束畫面為 Completing the Git Setup Wizard。 裝完一定要重啟 IDEA，否則持續提示 无法运行 Git. 未安装 Git. 下载并安装。 但本片即使重啟後仍未識別到，最後是靠 设置 → Version Control → Git → Path to Git executable 指向 git.exe 才成功。
    • 指令：
    git config --global user.name "zx993817"
git config user.name
git config user.mial
git config user.email
git clone https://gitee.com/zx993817/Heaven-ms-nap.git
    • 坑：⚠️ Git 安裝路徑三方不一致——v001 與口述都指向 <DRIVE>\Program Files\Git， 但 v004 的 IDEA 設定畫面填的是 <PROGRAMFILES>/Git\bin\git.exe。實際生效路徑無法從素材確定。 ⚠️ 安裝檔名不一致——Chrome 下載列顯示 Git-2.41.0.64-bit.exe，實際執行的是 Git-2.41.0.2-64-bit.exe。 ⚠️ 未裝 Git 就點 IDEA 的 Clone，會被騰訊電腦管家攔截並提示「发现软件正在发送安全...」，且不會拉取成功。

    W16-005　user.name 決定貢獻者名；user.email 只是唯一標識¶

    • 關鍵字：user.name user.email --global error: unknown key: user.mial 貢獻者
    • 來源：S4 08:00–10:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：user.name 是每次提交顯示的貢獻者名稱，必須設。驗證方式是去掉 --global 直接查詢： git config --global user.name "zx993817" → git config user.name 輸出 zx993817 即成功。 user.email 的定位講者講得很清楚：「這個郵箱是沒有關係的啊，並不是作為你登錄的一個依據。 它只是對應的一個……判斷你這個人、每個 Git 用戶的唯一標識的一個東西。 你可以隨便改，也可以隨便填，可以填 123456 都沒關係的。」 口述也提醒「注意，注意這裡的是 Git，不是 Git 11」（逐字稿把 Git 誤聽為 Git 11）。
    • 指令：
    git --global config user.name ""
git config --global user.name "zx993817"
git config user.name
git config user.mial
git config user.email
    • 坑：git config user.mial 是刻意的錯誤示範（mial 是 email 的誤字）， 錯誤原文為 error: unknown key: user.mial。不要把它當成正確寫法。 另外 git config user.email 在畫面上未返回結果，操作者因此還跑去看 Gitee 網頁的綁定信箱—— 這是因為前面根本沒設過。 ⚠️ 畫面另有 git --global config user.name ""（雙橫線）的錯誤示範，輸入到一半就刪掉了，正確寫法是單橫線。

    W16-006　IDEA 的 Clone 屢次失敗時改用 CMD git clone¶

    • 關鍵字：git clone 从版本控制获取 文件 → 打开 此窗口 (W) Cloning into
    • 來源：S4 10:00–12:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：IDEA 內建 Clone 兩次都沒成功（一次被攔截、一次一直提示沒有），講者放棄改用終端機：
    git clone https://gitee.com/zx993817/Heaven-ms-nap.git

    成功輸出（逐字，關鍵數值）：

    Cloning into 'Heaven-ms-nap'...
remote: Enumerating objects: 17359, done.
remote: Counting objects: 100% (17359/17359), done.
remote: Compressing objects: 100% (5348/5348), done.
remote: Total 17359 (delta 10023), reused 17359 (delta 10023), pack-reused 0
Receiving objects: 100% (17359/17359), 92.11 MiB | 487.00 KiB/s, done.
Resolving deltas: 100% (10023/10023), done.
Updating files: 100% (24217/24217), done.

    之後在 IDEA 走 「文件」→「打开...」 選目錄 <USERPROFILE>\Desktop\Heaven-ms-nap。 成功基準：objects 17359、pack 92.11 MiB、工作樹檔案數 24217。 - 坑：⚠️ 開啟視窗的選擇，口述與畫面相反——口述說「一般是選擇新窗口啊」， 但示範中實際點的是 「此窗口 (W)」。兩者都照登。 ⚠️ 本片沒有示範 IDEA 內成功 Clone 的畫面（口述說「剛在 IDEA 裡面 clone 也是 okay 的啊」， 但畫面兩次都失敗）。⚠️ 另有一則紅色 Git 錯誤「无效的 Git... 不支持向后...」僅辨識出部分， 因字體小且被快速關閉，完整原文無法確認；操作者選擇選單中的 不下载源码 忽略。

    W16-007　Project SDK 與 Module SDK 都必須指定 JDK 1.8¶

    • 關鍵字：项目结构 模块 SDK 无 SDK 语言级别 1.8.0_372 1.8.0_291 cores
    • 來源：S4 12:00–16:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：Project Structure 初始 SDK: 為 <无 SDK>，必須手動 + 添加 SDK → JDK...。 畫面先選 1.8 (Amazon Corretto version 1.8.0_372)， 語言級別設為 8 - Lambda, 类型注解等； 切到左側 模块 後，把 模块 SDK 改為 1.8 (Oracle OpenJDK version 1.8.0_291)， 並檢視 cores（口述稱「cores 是我們的依賴包目錄」）與 lib 資料夾。 口述還說「然後項目上我們還是改一下，給它改成依賴這個 Oracle 的 Open JDK」。
    • 坑：⚠️ SDK 版本口述與畫面衝突——口述說「最好還是跟我一樣用 202 的」， 但畫面只有 1.8.0_372 與 1.8.0_291，無 202；口述另說「1.8.4，看一下是不是這個」， 畫面則是 1.8.0_291。⚠️ 設定入口口述與畫面不一致——口述說「我們點擊設置」， 畫面是 文件 → 项目结构...；口述說 GBK 在「通用裡面……常規裡面」， 畫面路徑是 Editor → File Encodings。屬 IDE 版本介面差異，未能確認哪一版為準。 ⚠️ 專案名在畫面先後出現 heaven-ms-nap-2.x、heaven-ms-map、heaven-ms-map-2.x、heaven-ms-nap 四種， AutobanFactory.java 的路徑也有四種寫法，追程式碼前先確認手上是哪一份。
    • 相關：見 W01-009（課堂環境）

    W16-008　編碼要改 GBK，但改設定救不了既有亂碼¶

    • 關鍵字：File Encodings GBK 乱码 Reload Convert MOB_COUNT
    • 來源：S4 18:00–22:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：口述原話：「大家在開發之前記得把編碼格式改一下啊」， 以及「全局的你無所謂，項目的編碼一定要設置成 GBK，然後屬性文件的編碼也設置成 GBK」。 路徑：设置 → Editor → File Encodings，三項設定為 Global Encoding = GBK、Project Encoding = GBK、 Default encoding for properties files = GBK。 但改完設定後，已存在的亂碼註解不會自動修好，本片示範中必須手動重打：
    // 修改前（亂碼）
MOB_COUNT, // ﰴ ()

// 修改後（手動修正）
MOB_COUNT, // 击杀怪物数 超过正常(可能是吸怪)

    原因是檔案以 GBK 儲存但 IDE 以 UTF-8 讀取。 - 坑：編碼設定必須在開始改碼之前做，順序錯了要一個一個手動修。 編輯時右下角曾出現提示，提供 Reload／Convert 選項，但示範中未點擊—— 這個提示是可用的解法，別以為只能手打。

    • 關鍵字：2.x Commit 提交并推送 已推送到 origin/2.x AutobanFactory类增加注释
    • 來源：S4 20:00–24:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：口述：「比如說我們是要在 2.x……我們現在分了一個 1.x 分支和 2.x 分支啊， 我們 checkout 到 2.x 分支。然後在 2.x 分支上提交我們的這個漢化。」 實作：左側 Commit 工具視窗勾選 AutobanFactory.java → 填 Commit 訊息 → 點 「提交并推送... (Commit and Push...)」 → 彈出 「推送程式碼 (Push Commits)」 視窗， 確認目標 origin: 2.x → 點 「推送 (Push)」 → 右下角通知 「已推送到 origin/2.x」。 推送完成後自己的倉庫就有提交記錄，也跟主倉庫不一樣了。
    • 坑：⚠️ 分支在畫面上未出現 2.x——v003／v004 的 Git 面板與分支選單記錄的都是 master 與 origin/master；2.x 僅出現在 v005 的推送目標與 PR 設定中。 ⚠️ Commit 訊息不一致——v004 記錄為 修改了，v005 為 AutobanFactory类增加注释， v006 為 AutobanFactory修改，合併後顯示 AutobanFactory增加注释（無「类」）。 無法確定是多次提交還是解析誤讀，未臆測。

    W16-010　Gitee 上建立 PR #117 的九個介面步驟¶

    • 關鍵字：Pull Requests 新建 Pull Request #117 接受 Pull Request 已合并 目标分支
    • 來源：S4 22:00–26:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：PR 的定義講者也解釋了：「PR 就是 pull request 的首字母縮寫」。 分支對應規則：「我們新建一個 PR，然後前面就是我們自己倉庫…… 我們要合入主倉庫的 2.x 分支」。九個步驟與介面文案逐字：

    2 點擊 新建 Pull Request
    3 來源分支：zx993817:heaven-ms-nap 的 2.x
    4 目標分支：sleepnap/heaven-ms-nap 的 2.x（預設 master 需手改）
    5 標題：AutobanFactory类增加注释

    8 確認對話框 接受 Pull Request
    9 狀態更新為綠色 已合并

    合併後維護者端會看到 PR，審查通過才合併；之後在主倉庫的貢獻者名單就能看到你。 - 坑：⚠️ PR 目標分支預設是 master，本片必須手改成 2.x，這一步容易漏。 ⚠️ 貢獻者名單不會即時刷新——本片第一次搜貢獻者時講者說「呃，翻車。好吧。暫時還看不到啊」， 需要刷新才會出現（尾段 28:00 之後搜 Z 才看到「它提交了兩次」）。 ⚠️ PR 的描述欄位沒有實際填寫（口述只說「可以隨便填」「可以填也可以不填」）， 權限等級的完整選項也未展示——這兩處不可腦補。

    W16-011　成為開發者後要把 origin 從個人 fork 改指主倉庫¶

    • 關鍵字：Git Remotes origin 管理远端 https://gitee.com/sleepnap/heaven-ms-nap.git Fetch
    • 來源：S4 24:00–26:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：維護者端在 管理 → 專案成員 把使用者加為開發者後， 貢獻者端要開 「Git Remotes」 視窗，把 origin 的 URL 從 https://gitee.com/zx993817/heaven-ms-nap.git 改為專案主庫 https://gitee.com/sleepnap/heaven-ms-nap.git，然後執行 Fetch 取得遠端最新變更。 口述：「好，現在我們這個分支就變成主倉庫的分支了……後面我們所有的開發就在主倉庫裡面開發就好了， 不需要在自己 fork 的那個倉庫裡面去開發了。」
    • 坑：漏掉這一步，後續所有提交都會繼續推到自己的 fork，而且不會有任何報錯。 這是本片最無聲的失敗點。
    • 相關：見 W16-012

    W16-012　兩種方案：重新 Clone 主庫，或直接改 remote¶

    • 關鍵字：重克隆 remote zx 分支origin:zx Pushed 1 commit to origin/zx
    • 來源：S4 26:00–28:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：成為開發者後有兩種方案。講者逐字： 「第一種就是跟之前的一樣，克隆一下主倉庫的那個倉庫，然後拉下來，拉到本地來。 然後後面我們在 IDEA 的時候就打開主倉庫。第二個就是直接改，直接改分支啊。 然後我這裡就用第二種方法。」 第二種方案的示範提交是把兩個欄位加 final（理由是物件屬性初始化後不應被修改）：
    // 修改前
private int points;
private long expiration;

// 修改後
private final int points;
private final long expiration;

    Commit 訊息 AutobanFactory修改，推送 zx -> origin:zx， 結果通知 Push successful / Pushed 1 commit to origin/zx。 - 坑：⚠️ AutobanFactory 欄位名在兩段畫面不一致——18:00 前後是 private int points; / private long expireTime; 且 getter 為 getExpire()； 26:00 前後是 private int points; / private long expiration;。 ⚠️ ⚠️ 注意：口述說「我們就 checkout 到 2.x 分支」，但推送目標是 zx 分支—— 畫面上 2.x 與 zx 都沒出現在分支選單裡，分支對應關係無法從素材完全確認。

    W16-013　提交紀律：有說明、warning 可推、error 不可推¶

    • 關鍵字：提交說明 warning error 5 个错误 不要提交
    • 來源：S4 22:00–24:00、26:00–28:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：兩條紀律講者都重複強調過。 第一，每筆提交都要有提交說明，原話：「我們所有的提交都是有提交說明的。 大家最好給個提交說明啊。不然後面要找之前提交的記錄找不到。」 第二，推送前分辨 warning 與 error，原話：「如果是有五個錯誤的話，有五個 error 的話， 大家就就不要提交了，要好好檢查一下自己的代碼是不是有問題。如果是五個警告的話， 或者沒有任何警告的話，那就提交就好了。」本片第一次推送是 8 個 warning、 第二次是 5 個 warning，都照樣推了。
    • 坑：⚠️ 口述在 22:00 段說「提示有 8 個警告的地方……只要沒有提示有錯誤的地方就好了」， 但在 26:00 段的規則描述是「5 個 error 就不要提交」。兩處都以 warning 可推、error 不可推 為準。 ⚠️ 另外逐字稿把「Git 語法提示」誤聽為「JS 語法提示」—— 講者原意是說 IDE 社群版的 Git 語法提示較不友善（社群版可用，因本專案不涉及 Spring）。

    W16-014　AutobanFactory enum：外掛防護的扣分與判定時間結構¶

    • 關鍵字：AutobanFactory enum points expireTime DAMAGE_HACK FAST_HP_HEALING AutobanManager
    • 來源：S4 16:00–28:00｜S4_参与gitee项目开发教程_教學筆記.md
    • 要點：本片沒有寫新功能，唯一的「載體」是這個 enum——它定義了伺服器端各種外掛防護規則的 扣分標準（points）與判定時間（expireTime）。骨架：
    package client.autoban;

public enum AutobanFactory {
    MOB_COUNT, // 怪物数量 (有部分註解被遮擋)
    GENERAL, // 一般的断线
    FIX_DAMAGE, // 修复伤害异常
    DAMAGE_HACK(15, 60 * 1800), //伤害作弊 (参数:15次扣除分数)如果在规定时间内扣除分数过高,会触发系统封号处理(初始60分钟内统一处理异常情况)
    DISTANCE_HACK(10, 120 * 1800), //打怪距离过长 参数同上
    PORTAL_DISTANCE(5, 30000), //异常门距离作弊
    PACKET_EDIT, //封包修改
    ACC_HACK, //命中作弊
    CREATION_GENERATOR, //制造生成器作弊
    HIGH_HP_HEALING,
    FAST_HP_HEALING(15, 30000), //快速回血作弊 (参数:15次扣除分数)如果在规定时间内扣除分数过高,会触发系统封号处理...
    // ... 其他諸多列舉項目

    private int points;
    private long expireTime;

    private AutobanFactory() {
        this.points = -1;
        this.expireTime = -1;
    }

    private AutobanFactory(int points, long expire) {
        this.points = points;
        this.expireTime = expire;
    }

    public int getPoints() { return points; }
    public long getExpire() { return expireTime; }
}

    另有兩個被檢視（未修改）的 GachaExp 防作弊 handler，示範了兩種 Autoban 呼叫寫法：

    // 寫法一：AutobanManager 靜態取得 + return
AutobanManager.getInstance().autoban(c.getPlayer(), "Player tried to redeem GachaEXP, but had none to redeem.");
return;
// ...
c.announce(MaplePacketCreator.enableActions());

    // 寫法二：enum 直接呼叫（無 return、無 announce）
AutobanFactory.GACHA_EXP.autoban(c.getPlayer(), "Player tried to redeem GachaEXP, but had none to redeem.");
// 另一支用 AutobanFactory.PACKET_SPAM.autoban(...)
    • 坑：⚠️ Autoban 呼叫寫法在三個檔案中不一致—— UseGachaExpHandler.java 在 v001 用 AutobanManager.getInstance().autoban(...) ＋ return ＋ c.announce(MaplePacketCreator.enableActions())，v002 卻用 AutobanFactory.GACHA_EXP.autoban(...) 且沒有 return、沒有 announce；RewardGachaExpHandler.java 用 AutobanFactory.PACKET_SPAM.autoban(...)。 ⚠️ 這是防作弊路徑——缺少 return 會讓扣分後仍繼續執行 gainGachaExp()。 抄任何一版之前先確認是哪個分支的程式碼。 ⚠️ 檔案路徑同樣有四種寫法（heaven-ms-map/src/client/autoban/、 heaven-ms-nap-2.x/src/main/java/client/autoban/、heaven-ms-nap/src/client/autoban/、 src/server/autoban/（v006 為推測））。⚠️ 影片開頭出現的 RewardGachaExpHandler.java 片段 在 // ... 處截斷，不是可直接編譯的完整檔案。
